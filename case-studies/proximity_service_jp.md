# 近接サービス
[English Version](./proximity_service_en.md)

## 機能要求
- 半径20キロ距離内にあるビジネスを検索して表示する。ユーザはその検索半径を0.5キロ、1キロ、2キロ、5キロ、20キロと変更することができる。
- ビジネスオーナーは、ビジネスの追加、削除と更新をすることができるが、しかし、新しく追加または更新された情報はその翌日にならないと表示されないので、ユーザへの表示は常にリアルタイムに最新情報に更新する必要はない。
- ユーザは、自分を中心とする指定半径内にあるビジネスの詳細を表示させることができる。

## 非機能要求
- 低い遅延：ユーザは近隣にあるビジネスを素早くチェックできるようにする必要がある。
- データプライバシー：ユーザの位置情報はセンシティブに扱うべき。
- 高い有用性とスケーラビリティ：ユーザが大勢いる状況下でも動作するようにする必要がある。

## 概算
毎日1億のユーザと2億のビジネスがある環境を提として想定した場合、
各ユーザが毎日5回の検索をするとすると QPS = 1憶x5/10^5 = 5,000となる（一日にある秒の数は24x60x60=86,400であるため、10^5とおく）。

## 設計

### RESTful API

- 緯度・経度・半径の三つのパラメータを指定して、GET /v1/search/nearbyのエンドポイントをコールする。その結果として、以下のものがレスポンスとして受け取る。
```
{
    "total": 10,
    "businesses": [{business objects}]
}
```

- ビジネスの詳細情報を取得するには`GET /v1/businesses{:id}`
- ビジネス情報の追加には`POST /v1/businesses`
- ビジネス情報の更新には`PUT /v1/businesses/{:id}`
- ビジネス情報の削除には`DELETE /v1/businesses/{:id}`

### データモデル
読み出し/書き込みの比率が高いことが予想され、読み出しが非常に多いことから関係データベースのMySQLが非常に相性が良い。主なデータベーステーブルが二つあり、ビジネステーブルと地理空間インディクステーブルである。

### システム設計
システムは、位置情報サービスとビジネス関連サービスの二つのサービスからなる。位置情報サービスはユーザによる情報読み出しに対応し、ビジネス関連サービスは、ビジネスオーナーによるビジネス関連情報の更新に対応する。どちらのサービスも状態を持たないため、スケーラビリティの拡張はしやすい。近接サービスの検索


データベースクラスタは、プライマリーとセカンダリで構成する。データはプライマリーデータベースに保存され、それからセカンダリデータベースに複製される。セカンダリデータベースはかならずしもプライマリーデータベースと一致しないが、情報のリアルタイム表示が要求されないため、問題にはならない。

#### 近接サービスの検索
- オプション1：2次元検索
　所定半径で円を描き、縁の中に位置するビジネス情報のすべてを列挙する。このやり方はテーブル全体をスキャンする必要があり、効率的ではない。
```
SELECT business_id, latitude, longitude,
FROM business
WHERE (latitude BETWEEN {:my_lat} - radius AND {:my_lat} + radius) AND
      (longitude BETWEEN {:my_long} - radius AND {:my_long} + radius)
```
